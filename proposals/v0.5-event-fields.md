## The bar every field here has to clear

From `spec/v0.4/README.md` §Extensions and the reasoning behind `organizers`/`image`/`offers`/`cfp`:

1. **A real producer emits it** — or, failing that (the `cfp` exception), the value lives *inside the OTE
   ecosystem* and the producers publish it in HTML that consumers scrape today. Speculative design is
   forbidden.
2. **Additive and backwards-compatible.** Every new field is optional. A v0.2–v0.4 consumer that ignores
   it sees the exact same valid document. v0.5 stays MINOR.
3. **A list from the start if any producer emits several** (`organizers`, `image`). Widening object→list
   later is a breaking change.
4. **String-or-object entries** when the object only adds optional metadata (`image[]`). An array of
   objects would break already-published documents.
5. **Absent = unknown, never the tolerant value.** No default that lets a producer emit a false assertion
   without noticing (`attendanceMode`, `offers`, `availability`).
6. **No exact duplicates in a list** (`uniqueItems`, D024/D027).
7. **A translation table to the three destinations, including the honest loss.** Structural loss is
   acceptable; loss that produces *false* data is not.
8. **Recommended-tier only if the warning is actionable** — an `.ics` importer cannot act on a warning
   about something iCalendar does not model (`email`, `cfp`, `offers` are all *not* recommended).
9. **Proper nouns are never translated; prose and labels are**, with a `translations` map local to the
   object (never a positional mirror).
10. **URL fields are HTTP(S) IRIs** (v0.4), no embedded userinfo (`^https?://[^/?#]*@` forbidden).

## P035 — `speakers`: who gives the talk

**Area:** `event.schema.json` (`$defs`), `event.recommended.schema.json` (no change — argued below),
`reference.*.md`, `examples/`, `README.md`.

### Problem

`spec/v0.4/README.md` lists "modelling speakers/agenda/sponsors" in *"What v0.4 does not solve"* (line 844)
and, in the `organizers` section (line 414), names it as one of the three confusions to defuse:
*"`organizers` are not speakers. Whoever gives the talk is not modelled in v0.4 … Putting a speaker in
`organizers` corrupts the data for everyone who consumes it."* The spec warns against the wrong answer and
offers no right one. A directory that wants to show "who's speaking" — the simplest case, a meetup with one
speaker — has nowhere to put it without an unprefixed extension that is not interoperable between producers.
The Extensions table (line 821) already pre-names `speakers` as a **core candidate**.

### Evidence

- Of the five JSON-LD sources studied ([`research/findings/json-ld-event-platforms.md`](../research/findings/json-ld-event-platforms.md)),
  **none** emits `performer`. Only Google's canonical example carries it (`"performer": {"@type":
  "PerformingGroup", "name": "Kira and Morrison"}`), for a music act.
- **But Google reads `performer`** for the Event rich result (listed under *Recommended properties*:
  *"`performer` (Person or PerformingGroup) — The participants performing at the event, such as artists and
  comedians."*). schema.org: *"A performer at the event — for example, a presenter, musician, musical group
  or actor."*
- The real producers are conference sites and CFP platforms (Sessionize, Pretalx) that publish speakers in
  **HTML**. Directories like developers.events and confs.tech carry speaker data maintained by hand. This
  is the `cfp` situation: the value is inside the OTE ecosystem.

So `speakers` clears the bar the way `cfp` does (§1's exception), and has a *better* destination story than
`cfp`: one clean schema.org mapping that Google actually consumes.

### Proposal

Event-level, optional, **a list**. Reason for a list: co-talks, panels and fireside chats are normal, not
exceptional — the same argument as `organizers`, and schema.org `performer` is already repeatable.

```jsonc
"speakers": [
  { "name": "Ada Lovelace", "url": "https://ada.example",
    "sameAs": ["https://fosstodon.org/@ada"] },
  { "type": "organization", "name": "The Rust Survey Team" }
]
```

`$defs`:

```jsonc
"speakers": {
  "description": "Who gives the talk(s) — NOT who runs the event (that is organizers) and NOT where the data came from (source). A list in DISPLAY / preference order: the first is the one that survives to a single-value destination, the same rule organizers and image state. Co-talks and panels are normal. One document is one occurrence, so in a multipart conference the speakers of a given talk live on that talk's document, not on the parent. Distinct entries are never deduplicated by inferred identity — only exact repeats are rejected.",
  "type": "array",
  "minItems": 1,
  "uniqueItems": true,
  "items": { "$ref": "#/$defs/speaker" }
},
"speaker": {
  "type": "object",
  "required": ["name"],
  "properties": {
    "name": {
      "description": "Display name of the speaker. A proper noun: never translated.",
      "type": "string", "minLength": 1, "pattern": "\\S",
      "examples": ["Ada Lovelace", "Grace Hopper"]
    },
    "url": {
      "description": "The speaker's canonical page — their own site, or their main profile. One URL. Same rules as organizers[].url. Other profiles go in sameAs.",
      "type": "string", "format": "iri", "pattern": "^https?://",
      "not": { "pattern": "^https?://[^/?#]*@" },
      "examples": ["https://ada.example"]
    },
    "sameAs": {
      "description": "Other profile pages for the SAME person — Mastodon, LinkedIn, GitHub, a personal site distinct from url. A list; order not significant; only exact repeats rejected. Maps to schema.org Person.sameAs. Google's Event rich-result docs do not document nested performer.sameAs — the value is generic schema.org consumers and OTE directories. URLs, so no translation.",
      "type": "array", "minItems": 1, "uniqueItems": true,
      "items": { "type": "string", "format": "iri", "pattern": "^https?://",
                 "not": { "pattern": "^https?://[^/?#]*@" } },
      "examples": [["https://fosstodon.org/@ada", "https://www.linkedin.com/in/ada-lovelace"]]
    },
    "type": {
      "description": "Person or organisation. A translator picks a schema.org @type either way, and Person is the tolerant choice for a speaker.",
      "enum": ["person", "organization"],
      "default": "person"
    }
  }
}
```

Add `speakers` to `$defs/event.properties`, placed after `organizers` in declaration order (both answer
"who is behind this") — see §Field order below. No `required` entry anywhere.

**`url` is one canonical URL; `sameAs` is the list of other profiles.** hhkaos raised the multi-URL case
(social profiles), citing [techconf.directory](https://github.com/DeclanChidlow/techconf.directory)'s
speaker records (`website` + a `socials` map). `url` stays a single canonical page (parallel to
`organizers[].url`); **`sameAs` is a list of other profile IRIs for the same person** — Mastodon,
LinkedIn, GitHub, a personal site.

```jsonc
"speakers": [
  { "name": "Ada Lovelace", "url": "https://ada.example",
    "sameAs": ["https://fosstodon.org/@ada", "https://www.linkedin.com/in/ada-lovelace"] }
]
```

`sameAs`: array, `minItems: 1`, `uniqueItems: true`, **HTTP(S) IRI** + no embedded userinfo — the same
rules every URL field in the spec follows. Order not significant. **It is `sameAs`, not `url` becoming
string-or-array**, so the *canonical* page stays a single unambiguous value (what a single-value
destination uses) and the extras are clearly secondary.

**HTTP(S) only — not a DID / AT-URI / `acct:` handle** (Codex Round 10). schema.org `sameAs` is *"the URL
of a reference Web page"*, not an identifier. techconf.directory stores a Bluesky DID and a Fediverse
handle; the OTE form is the **public HTTPS profile URL** (`https://bsky.app/profile/<handle>`, the
Mastodon profile page). Raw decentralised identifiers stay an extension until there is a dedicated
identity-field proposal — the same line D020 draws for `id`.

> **`sameAs` in the core is hhkaos's call, over Codex Round 9.** Codex recommended keeping it in P038:
> schema.org `Person.sameAs` is the right vocabulary, but Google's Event rich-result docs do **not**
> document a nested `performer.sameAs`, so there is no Google producer/consumer pull, and no measured
> producer bar. The counter (same as `recordings`): it is cheap (URLs, no translation, existing rules),
> techconf.directory's `socials` map *is* this data, and the multi-URL case is the one thing hhkaos
> actually asked for. The mapping claim is **softened** accordingly — see the table below.

**Still NOT in the core** — `affiliation`, `jobTitle`, `bio`, `image`/`photo`, `location`, pronouns, any
identifier. The `organizers` discipline ("no logo, no identifiers — describe who they are and where to
find them"). Concretely:

| Field | Where it went, and why |
| --- | --- |
| `sameAs` (multi-URL) | **In the core.** Array of profile IRIs → schema.org `Person.sameAs`. Google's Event docs do not promise nested-performer `sameAs`, so the value is generic schema.org consumers + OTE directories, not a Google rich result. |
| `affiliation` | **P038.** Cheap (one org *display* name, a proper noun — written once, not translated, same rule as `organizers[].name` / locality spellings). Deferred for lack of a producer bar; likeliest of the P038 set to graduate. |
| `jobTitle` | **P038.** Free text → a local `translations` map on graduation (D010/D023/D030). |
| `bio` | **P038.** Same translations cost, larger (prose). |
| `image`/`photo` | **P038.** Reopens the entire `image[].alt` accessibility apparatus nested inside `speakers[]`. Highest cost, weakest use ("pretty cards"). Its `translations` are **not** core-validated as an extension. |
| `location`, pronouns | **P038 / not yet.** Niche; no producer. |

The P038 ones are **not dropped** — they are a documented `speakers` enrichment shape so
techconf.directory / Sessionize / Pretalx converge on one form, with **per-sub-field adoption counting**
so `affiliation` can graduate without dragging `bio`/`image` translation cost.

**`type` default is `person`**, the opposite of `organizers` (`organization`). A speaker is overwhelmingly
a person; an organisation "performing" is the rare case (a working group presenting collectively). The
tolerant choice follows the common case.

### Field order

```
id, url, name, description, image, organizers, speakers   ← what it is and who is behind it
```

`speakers` sits next to `organizers`, after it: you announce *that there is an event and who runs it*
before *who is on stage*.

### Compatibility impact

Purely additive. No v0.2–v0.4 document becomes invalid. A consumer that does not know `speakers` ignores an
unknown property, exactly as today. `speakers` in `organizers`-style extension form (unprefixed) that some
producer already ships becomes normative with the same shape.

### Recommended profile

**Not recommended.** Two reasons, both already used for `email`/`cfp`: (a) an `.ics` importer never has
speaker data — iCalendar does not model it — so the warning is not actionable; (b) most events in a
community feed are meetups whose "who's speaking" is often the organiser anyway, so a warning would fire on
the majority for no gain. It can be promoted later if a producer ecosystem appears, the same way the
recommended list is allowed to grow.

### Translation to the three destinations, including the loss

| Destination | Mapping | Loss |
| --- | --- | --- |
| **schema.org** | `performer` (array): `@type` `Person` for `person`, `Organization` for `organization` (Google accepts both); `name` → `name`; `url` → `url`; **`sameAs` → `Person.sameAs`** (array, 1:1). | None in the model. Google reads `performer`/`name`/`url` for the Event rich result; it does **not** document a nested `performer.sameAs`, so those extra profiles reach generic schema.org consumers and OTE directories, not a Google rich result. |
| **iCal** | **RFC 5545 core has no speaker term; the normative fallback is `X-OTE-SPEAKER:Ada Lovelace` (repeatable) or a line in `DESCRIPTION`.** As an *optional advanced export*, enhanced iCalendar (RFC 9073, Standards Track, *Updates: 5545*) MAY emit one `PARTICIPANT` component per speaker: `PARTICIPANT-TYPE:SPEAKER` and `UID` are **required** by RFC 9073 §7.1 (the exporter mints the `UID` from `speakers[].url` when present, else from `<event id>` + a stable slug of `name`), `SUMMARY` carries `name` (**not** `CN` — `CN` is an `ATTENDEE`/`ORGANIZER` parameter, not a `PARTICIPANT` property), `URL` carries `url` when present. `ATTENDEE` stays forbidden — it means a participant/invitee, not a speaker. | Total for a core-5545 client, and **harmless**: it still shows the whole event. An RFC 9073-aware client gets the speakers — at the cost of the exporter minting a participant `UID` the OTE model does not carry. |
| **RSS / Atom** | Nothing native → the item body ("Speakers: Ada Lovelace, …") | Total, harmless. |

Degrading to *ignored* in two of three is the same trade `partOf` and `offers` already accept: an identity
field that gets ignored leaves incomplete data, not false data.

### Alternatives considered

- **A single `speaker` object, not a list.** Rejected by rule 3: panels and co-talks are real and common,
  and `performer` is already an array. Widening later breaks.
- **Reuse `organizers` with a `role` field.** Rejected: it is exactly the corruption the spec's own prose
  warns against — a consumer that does not read `role` attributes the talk to the speaker as organiser.
- **`performers` as the field name** (matching schema.org). Rejected: the Extensions table already
  pre-named `speakers`, it is the word the audience uses, and the schema.org term is reached by mapping,
  not by mirroring (same as `venue`≠`Place.name`, `geo`≠`GeoCoordinates`).
- **Per-talk nesting under `partOf`.** Rejected: "one document = one occurrence" already gives each talk in
  a `multipart` conference its own document; `speakers` on that document is the per-talk field with no new
  nesting.
- **Include `affiliation`.** Deferred: no structured producer, and it drags in translation. Revisit if a
  real feed emits it.

### Revisit if

A producer ecosystem for structured speaker data appears (a CFP platform emitting JSON-LD `performer` at
scale), at which point `bio`/`affiliation` and possibly recommended-tier promotion should be re-examined
together.

## P036 — `recordings`: the video, after the event

**Area:** `event.schema.json` (`$defs`), `reference.*.md`, `examples/`, `README.md`. No recommended-profile
change.

### Problem

Communities record their talks and upload them to YouTube/PeerTube afterwards; directories and aggregators
want to link the recording from the event document instead of forcing a separate search. Today there is
nowhere to put it, and unlike speakers this is **not even an acknowledged gap** — it appears nowhere in
`README.md` or `DECISIONS.md`. No existing field covers it:

- `image[]` is explicitly "the poster / cover / card", and its entries are validated as image files.
- `source.url` points at **where the event data came from** (an `.ics`, a Meetup page), not at a recording.
- `location.onlineUrl` is the **live** connection link, which usually stops meaning anything — or changes
  meaning — once the event is over.

This is data added **after** the event is published: the document already exists with its stable `id`, only
`updatedAt` changes.

### Evidence

- Of the five JSON-LD sources studied, **none** emits any recording/video property.
- **Google reads no video property for `Event`** (checked against the Event structured-data doc: no
  `video`, `recordedIn`, `workFeatured` or `subjectOf` in the supported list).
- schema.org **does** have the exact term: `recordedIn` — *"The CreativeWork that captured all or part of
  this Event."* Range `CreativeWork` (a `VideoObject` is one).
- The real-world producers are the communities themselves (YouTube/PeerTube channels) and directories that
  curate "watch the talk" links by hand.

So `recordings` is the **weakest** of the three on the producer bar: no structured producer, and no
destination that *shows* it. Its entire justification is the `cfp` one — a value that lives inside the OTE
ecosystem — and it is thinner than `cfp`'s, because `cfp` at least answers a time-sensitive discovery
question ("is it open right now?") that a scraped directory maintains at cost.

> **Verdict — `recordings` GOES INTO v0.5.** (hhkaos direction 2026-08-31; confirmed 2026-08-31 over the
> P038-page alternative.)
>
> Codex Round 1 was right that `recordings` clears neither the plain admission bar nor the `cfp`
> exception on producer evidence. hhkaos overrode the weight of that: the field is cheap (one `$defs`,
> the `image[]` pattern, zero interaction with other rules), the schema.org target (`recordedIn`) is
> clean, and the `0.x` / near-zero-adoption / "can break without warning" context means the "wait for a
> producer" bar is a luxury the spec cannot really afford to hold this small a field to. It is **not
> recommended-tier** (an importer never has it; a future event has no recording yet), so it costs a
> producer nothing and a consumer one `typeof` check.
>
> The [P038](#p038--a-suggested-extensions-section-on-the-site) page is for fields that are *not* cheap
> and *not* obviously right; `recordings` is cheap enough to skip that queue.

### Schema (Round-1 fixes folded in)

Event-level, optional, **a list** (a talk on YouTube *and* a community PeerTube mirror; or the talk and its
Q&A uploaded separately). Entry is **a bare HTTP(S) IRI string or an object** — the `image[]` pattern, so
it can be widened without a breaking change.

```jsonc
"recordings": [
  "https://www.youtube.com/watch?v=dQw4w9WgXcQ",
  { "url": "https://tube.rustmadrid.example/w/abc123", "title": "Q&A" }
]
```

`$defs`:

```jsonc
"recordings": {
  "description": "Published recordings of the event, added AFTER it happened (same id, new updatedAt). NOT location.onlineUrl (that is the live link) and NOT image (that is the poster). A list — a talk may be on more than one platform, or split into parts. Two entry forms, like image: a bare HTTP(S) IRI, or an object adding a title.",
  "type": "array",
  "minItems": 1,
  "uniqueItems": true,
  "items": {
    "oneOf": [
      { "type": "string", "format": "iri", "pattern": "^https?://", "not": { "pattern": "^https?://[^/?#]*@" } },
      { "$ref": "#/$defs/recordingEntry" }
    ]
  }
},
"recordingEntry": {
  "type": "object",
  "required": ["url"],
  "properties": {
    "url": {
      "description": "Absolute HTTP(S) IRI where the recording can be watched. A watch page (YouTube, PeerTube) is fine here — unlike image, this does not have to be the media file itself.",
      "type": "string", "format": "iri", "pattern": "^https?://",
      "not": { "pattern": "^https?://[^/?#]*@" }
    },
    "title": {
      "description": "What this recording is, when the list has more than one ('Q&A', 'Full session', 'Lightning talks'). Noise when there is only one. Free text, in the document's textLanguage — translated by this entry's own translations map, like image[].alt.",
      "type": "string", "minLength": 1, "pattern": "\\S"
    },
    "translations": {
      "description": "This recording's title in other languages. Local to the entry, never a positional mirror. Requires the document's textLanguage, and is policed by the same D010/D023/D030 rules as image[].translations.",
      "$ref": "#/$defs/recordingTranslations"
    }
  },
  "dependentRequired": { "translations": ["title"] }
}
```

Round-1 fixes folded in:

- **HTTP(S), not `https`-only.** v0.4/P034 deliberately moved every URL field to `^https?://` IRIs and even
  relaxed images to accept `http://` (`docs/history/CHANGES.log:2863-2869`). A community self-hosted archive
  over plain HTTP is no less plausible than an image over HTTP, and there is no evidence that an `http`
  recording produces *false* data — just a less ideal link. `recordings` reuses the shared HTTP(S) rule.
- **`title` gets a local `translations` map** (`recordingTranslations`, mirroring `imageTranslations`) plus
  `dependentRequired: {translations: [title]}` — every other nested free-text field in v0.4 has this
  (`image[].alt`, `offers[].name`, `partOf.name`, `eligibility.note`), and D010/D023/D030 plus the base
  `textLanguage` requirement enumerate those maps explicitly. Omitting it would open a hole (a
  `translations` map that does not require `textLanguage`) that Codex verified is real.
- **`uniqueItems` is not deduplication.** It rejects only exact JSON repeats (D024/D027). A bare URL and an
  object with the same `url` both naming one recording still validate; a consumer may still need
  URL-level dedupe. The checklist item "no exact duplicates" is not oversold as more than that.

**No `language` sub-field.** Considered (dubbed/subtitled versions), dropped: no producer emits it. A
dubbed version is just another entry with a `title`.

**No `type`/`mimeType`, no duration, no thumbnail.** A recording is a link; anything more is a `VideoObject`
and that is not what an event directory holds.

### Compatibility impact

Additive. A v0.2–v0.4 document that used `recordings` as an unprefixed extension keeps its exact shape;
one that did not is unaffected. A consumer that does not know the field ignores it. **One caveat** — the
same §Extensions collision risk that applies to any unprefixed field: a producer who already ships
`recordings` with a *different* shape (e.g. a bare string that is a page, not a media/watch URL) would
need to adjust. That risk is inherent to how the spec grows, and small here.

### Recommended profile

**Not recommended.** Most events have no recording; the warning is not actionable for an importer or for
a live event that has not happened yet, and the spec has no "is in the past" predicate. This is a
deliberate, permanent "not recommended" (like `email`/`cfp`), not "moot pending a decision".

### Translation to the three destinations, including the loss

| Destination | Mapping | Loss |
| --- | --- | --- |
| **schema.org** | `recordedIn` (array of `VideoObject { url, name? }`) — *"The CreativeWork that captured all or part of this Event"* | **Structural, and it does not reach Google** — Google reads no video property for `Event`, so the recording never appears in a rich result. A generic schema.org consumer that follows `recordedIn` gets it. |
| **iCal** | No term (RFC 7986 has no recording property). `URL` is taken by the event page. Degrade to `X-OTE-RECORDING` (repeatable) or a `DESCRIPTION` line | Total; harmless. |
| **RSS / Atom** | A watch-page URL is **not** a direct media URL, so **not** `<media:content url>` (Media RSS 1.5.1: `media:content@url` "should specify the direct URL to the media object"; a player page belongs in `media:player url`). Map a watch page to `<media:player url>` or an item/body link. `<enclosure>` is also wrong — it forces `type`+`length` OTE does not model. | Structural. |

### Alternatives considered

- **A single `recordingUrl` string.** Rejected by rule 3 — multi-platform and split recordings are the
  norm for communities that record at all.
- **Keep it out of the schema, as an unprefixed extension.** This was the Round 1–3 outcome, reversed by
  hhkaos: the classic "wait for a structured producer" bar is a luxury for a field this cheap given
  `0.x` + near-zero adoption. If the review or hhkaos still prefers it, `recordings` becomes the **first
  entry on the P038 page** with the exact same shape — the schema work is not wasted either way.
- **`video` as the field name** (schema.org-ish). Rejected: "recordings" is what a community calls it, and
  it is broader (an audio-only recording, a slides+audio capture).
- **Attach the recording to `speakers[]` or to a future per-talk agenda.** Rejected: a recording is of the
  whole occurrence (which, in a `multipart` conference, is already one talk per document).

### Revisit if

A "past events archive" profile of the feed makes a recommended-tier warning meaningful, or a producer
emits `type`/duration/thumbnail often enough to justify widening the entry object.

## P037 — the single registration of a multi-part event

**Area:** `README.md` (§`partOf`), possibly `event.schema.json` (`$defs/partOf`), `reference.*.md`,
`examples/`.

### Problem

`spec/v0.4/README.md` admits this gap in two places:

1. §`partOf` (line 258): *"What `multipart` does not fix is 'a single registration': that is not a date.
   `offers` describes the price and registration of each document, not one registration shared across the
   parts — and v0.4 does not model that."*
2. *"What v0.4 does not solve"* (line 844): *"the box office: capacity, places left, discount codes and the
   single registration of a multi-part event."*

In a paid conference modelled as `multipart` (each talk/session its own document, shared `partOf.id`), you
normally **pay once for the whole thing**, not per session. Today:

- If each part carries its own `offers`, a consumer cannot tell whether that is (a) the real price of that
  session sold separately, (b) a redundant copy of the whole-conference price, or (c) — most common —
  `offers` absent on the parts.
- Case (c) is a trap: the spec **forbids** inferring "absent `offers` = free" (line: *"an absent offers
  list means the price is unknown"*). So a consumer seeing a paid `multipart` conference's sessions with no
  `offers` cannot conclude anything, and there is **no rule** saying "if the parent has `offers` and the
  parts do not, the price is the set's".

### The full case matrix (this is what "cover all cases" means)

| # | Shape | Real example |
| --- | --- | --- |
| **C1** | One price covers the whole set | 3-session study jam, single €0 / €X registration |
| **C2** | Tiered admission covers the whole set | DevFest early-bird / general / student — one ticket, every talk |
| **C3** | Admission **plus** a paid add-on per part | PyCon: conference ticket + $150 per tutorial; TRGcon workshops |
| **C4** | Admission plus some parts free to everyone | paid conference, public keynote open to all |
| **C5** | A part sold standalone — no admission needed | buy one workshop without a conference ticket |
| **C6** | The set's parent is **not** published as an OTE document | any of the above where `partOf.id` is an HTML-only page |
| **C7** | The whole conference is one document, with paid workshops alongside | one-day conf as a single doc + workshop docs that reference it |

### Evidence

- `spec/v0.4/examples/feed-multipart.json` and `event-recurring.json` — the modelled `multipart` shape,
  none with a shared-registration price.
- **C3 is not hypothetical.** PyCon US has charged conference registration + a separate per-tutorial fee
  for years; hhkaos cites [trgcon.com](https://www.trgcon.com/), where a workshop slot is reserved with —
  and can be added after — the conference ticket. Add-on pricing is a standard conference shape, not an
  edge case.
- schema.org: `subEvent`/`superEvent` carry price fine in the model, but **Google does not read
  `superEvent`/`subEvent`** (stated in the `partOf` table itself). So price that lives only on the parent
  is invisible in every per-talk rich result — an **inherent** loss no model here fixes.

### Proposal — a concrete model, breaking changes on the table

> hhkaos direction (2026-08-31): "open gap" is not acceptable; earlier rules/decisions may change; the
> `0.x` / near-zero-adoption / breaking-changes-notice context means backwards compatibility is a weak
> constraint. So this is a **real proposal**, and v0.5 may be a breaking `0.5.0`.

Two schema additions and one scoped rule. Between them they cover C1–C7.

#### (1) `partOf.offers` — the set's shared admission

An `offers` list (reusing `$defs/offers` verbatim) inside the `partOf` object. Semantics: **the price of
admission to the whole set**, written identically on every part that carries it, so a consumer holding a
single part document can price it without fetching the parent (→ **C6**).

```jsonc
"partOf": {
  "id": "https://trgcon.example/2026",
  "name": "TRG Conf 2026",
  "url": "https://trgcon.example/2026",
  "type": "multipart",
  "offers": [
    { "name": "Early bird", "price": 180, "currency": "EUR", "url": "https://trgcon.example/tickets", "closesAt": "2026-09-01T23:59:59+02:00" },
    { "name": "General",    "price": 240, "currency": "EUR", "url": "https://trgcon.example/tickets" }
  ]
}
```

→ covers **C1** (one entry, price 0 or X) and **C2** (tiered) directly.

#### (2) `offers[].scope` — what a part's own `offers` entry means relative to the set

A new optional enum on each `offer` entry, only meaningful when the document has `partOf`:

| `scope` | Meaning | Total cost to attend this part |
| --- | --- | --- |
| **`admission`** *(what an absent `scope` is read as)* | A complete way to attend this part — either the part is sold standalone, or this entry just restates the set admission | this entry's `price` (or "unknown, registration at `url`" if the entry is URL-only) |
| **`add-on`** | An **additional** charge on top of the set admission | a priced `partOf.offers` entry **+** this entry's `price`, when both carry a number; otherwise **"there is an additional charge, total unknown"** |

**Round-4 fix — `add-on` requires the set admission *in the same document*.** The schema enforces
`if any offer has scope: "add-on" then partOf AND partOf.offers are required` (validator name
`addOnRequiresSetAdmission`). Codex Round 4 found the earlier draft only required `partOf`, so
`offers: [{ scope: "add-on" }]` with a bare `partOf: { id, name }` validated and left the add-on
*relationship* undefined. `partOf.offers` is now required, full stop.

**Round-5 clarification — the number can still be unknown, and that is fine.** `$defs/offer` allows a
`price`, a `url`, or both (v0.4 — "registration exists, price not published yet" is a legitimate state).
So `partOf.offers` or the `add-on` entry may be URL-only. When either side has no `price`, a consumer
knows **there is an additional charge and where to pay it**, just not the total — which is strictly more
than v0.4, where the add-on relationship could not be expressed at all. This is the spec's "incomplete is
acceptable, false is not" principle: no number is emitted, so no wrong number is emitted. The recommended
profile warns (see below) so a publisher who *can* give the base price does.

```jsonc
// A paid tutorial that is its own document, part of the conference:
"partOf": { "id": "https://trgcon.example/2026", "name": "TRG Conf 2026", "type": "multipart",
            "offers": [ { "name": "General", "price": 240, "currency": "EUR", "url": "https://trgcon.example/tickets" } ] },
"offers": [
  { "name": "Testing workshop", "price": 60, "currency": "EUR", "scope": "add-on",
    "url": "https://trgcon.example/tickets#workshops" }
]
// → cost to attend this workshop = 240 (admission) + 60 (add-on)
```

→ **C3** (add-on). **C4** — a free public keynote part: `offers: [{ "price": 0, "scope": "admission", "url": "…/rsvp" }]` ("free, no ticket needed"); a session free *only to ticket-holders* is `{ "price": 0, "scope": "add-on" }` (which then also requires `partOf.offers`). **C5** — a standalone workshop: `offers: [{ "price": 80, "scope": "admission" }]`, and it can *also* list an add-on entry for ticket-holders — the list handles both at once. **C7** — the same, whether the parent is one document or many.

#### (3) The one scoped rule change — and it *is* a breaking change

> **In a document that has `partOf` carrying `partOf.offers`, a part that omits its own `offers` is
> *covered by the set admission* — its cost is exactly `partOf.offers`, not "unknown".** This is the only
> context in which an absent `offers` list has a defined meaning other than unknown, and it is defined
> *because the set-level price is present in the same document*. Everywhere else, absent `offers` still
> means unknown.

The Round-1 blocker (silent parent→part inheritance) does not apply — this rule fires only when
`partOf.offers` is present, a v0.5 construct. **But Codex Round 4 is right that "no v0.4 document can
contain it" is too strong**: §Extensions explicitly allows unprefixed core-candidate fields, so a v0.4
producer *could* already ship `partOf.offers` (or `offers[].scope`) with a local meaning. Standardising
these names is therefore a **collision** for that producer — exactly the risk §Extensions warns about.
So this is recorded as an **intentional `0.5.0` breaking change**, with:

- a `CHANGELOG` entry and a migration note;
- a scan of the registered adopter feeds (`docs/data/`) for `partOf.offers` / `offers[].scope` /
  `speakers` / `recordings` before finalising — if any adopter already uses one of these keys with a
  different shape, that shapes the migration note;
- a new `DECISIONS.md` entry (see "Decisions touched" below).

#### Consumer algorithm (per part)

```
admission = document.partOf.offers ?? none          // in-document only; partOf.id is NOT resolved for pricing
own       = document.offers ?? none

if own == none:
    cost = admission                                 // covered (rule 3); or unknown if admission is none
else:
    for each entry in own:
        if entry.scope == "add-on":                  // admission is guaranteed present by the schema
            base = a priced entry in `admission` (a consumer picks one, e.g. the cheapest, and says so)
            line item = (base.price + entry.price)   if both are numbers
                        "admission + <entry.price> extra"   if only the add-on has a price
                        "admission + extra fee, see <entry.url>"   if the add-on is URL-only
        else:
            line item = entry.price   if it has one, else "see <entry.url>"    // standalone / admission-shaped
    cost = the set of line items (a consumer shows them all, like tiered offers today)
```

### What this model does NOT cover — and stays ticketing

Codex Round 4: "C1–C7 do not exhaust real conference pricing." Correct. The following are **explicitly out
of scope for v0.5**, the same call v0.4 already makes for "discount codes, team rates, and the single
registration of a multi-part event":

- **Tier-specific coverage** — "workshop A is available only to *Full* tickets, not *Student*". `scope:
  "add-on"` means "on top of *any* admission tier"; there is no offer-to-offer relation.
- **Per-day passes for a multi-day conference** — a Friday talk whose set admission lists Friday /
  Saturday / Full passes cannot say *which* passes cover it.
- **Bundles** — "pick 3 of 5 workshops for €X", "workshop ticket includes the Friday conference day".
- **Group rates, coupon-only discounts, quantity pricing.**

If a real producer needs tier-specific coverage or per-day passes, the extension is **Model B**: give
`partOf.offers[]` stable `id`s (unique within the set) and add `offers[].dependsOn: ["<offer-id>", …]`
to an add-on, meaning "requires holding one of these admission offers". Model B is *not* proposed for
v0.5 — it is the documented next step, gated on a producer who actually needs it. Model A (flat) covers
**one shared admission (any tier) + flat add-ons** — which is what `trgcon.com` and PyCon-style
"conference + flat tutorial fee" need. It does not claim to cover conference pricing in general.

### Compatibility impact

- **`partOf.offers`, `offers[].scope`** — additive at the schema level; a **collision-class breaking
  change** at the §Extensions level (see rule 3 above). `0.5.0`, with a CHANGELOG entry.
- **`partOf.offers[].translations`** pulls in four rule-site updates Codex verified in Round 1 — the base
  `textLanguage` requirement enumeration, `distinctTranslationLanguages` (D010), the D030 `offers[].name`
  warning, generated reference paths, invalid-example corpus. **Accepted implementation cost.**
- **`offers[].scope`** — absent is defined (= `admission`-shaped), documented the way `attendanceMode`'s
  absence is.
- **Rule (3)** narrows "absent `offers` = always unknown" to "unknown *unless* `partOf.offers` is present
  in the same document". A v0.4 doc bumped to `0.5.0` without adding `partOf.offers` is unchanged.
- **The "`partOf` is safely ignorable" guarantee changes** — and Codex Round 4 is right that this is a
  **normative guarantee**, not a field description. `reference.en.md` and `README.md` both state a
  consumer that ignores `partOf` still sees correct events, and call `partOf` degrading to *ignored*
  "precisely the design". After P037, a consumer that ignores `partOf` can report a covered paid session
  as "price unknown" though the same document carries the price in `partOf.offers`. New wording:
  *"`partOf` stays safely ignorable for **grouping and identity**. A consumer that needs correct pricing
  for a multi-part event MUST also read `partOf.offers`. Ignoring it yields **incomplete** pricing (a
  missing price), never **false** pricing — consistent with the spec's 'incomplete is acceptable, false
  is not' principle."* This wording change lands **everywhere** `partOf` is described as harmlessly
  ignorable (README §`partOf`, both reference files) and gets a `DECISIONS.md` entry.

### Cross-part contradiction — `sharedOffersConsistent`

`partOf.offers` on sibling parts that share a `partOf.id` **must be equal by value**. A feed-root
validator error via a custom keyword — same mechanism and structural reason as D011's `uniqueEventIds`
(only the feed root sees siblings). D011 specifies "exact string equality"; this one is over nested
JSON, so it needs its own definition (**this is the new `DECISIONS.md` entry Codex asked for**):

- **Array order is significant** — `offers` is an ordered list, like `image[]` / `organizers`.
- **Object member order is not significant** — including members of a nested `translations` map.
- **Numbers compare by JSON value** — `45` ≡ `45.0`.
- **Strings compare exactly** — no case folding, no URI normalisation (same as D011).
- **`null` is treated as absent** — `{ "price": null }` ≡ `{}` for this comparison. (The base schema
  already rejects `null` where a type is required, so this is belt-and-braces.)
- **Siblings that *omit* `partOf.offers` are allowed** — a part may be described before its price is set.
  Once P037's recommended-profile pricing-completeness check exists, "some siblings carry it, others
  don't" is a **warning**, not an error.
- Fallback if a hard error is judged too heavy: the whole thing is a recommended-tier warning. It must
  not be left undefined.

A reference implementation and a feed-level test are in `proposals/validate-fragments.mjs` (a compact
`deepEqualJson` plus a `sharedOffersConsistent` check over a two-part feed) — see the run output.

### Recommended profile

- **`multipart` part with `partOf`, no `partOf.offers` anywhere in the set, and no own `offers`** →
  warning (the pricing question the set exists to answer is unanswerable). Feed-root keyword (same limit
  as D016).
- **`offers[].scope: "add-on"` present but no `partOf.offers[]` entry carries a `price`** → warning
  (Round-5). The add-on relationship is stated but no consumer can compute a total. Actionable: the
  publisher knows the base price. A per-event check suffices — `partOf.offers` is in the same document.
- **`offers[].scope: "add-on"` without `partOf.offers` at all** → already a **base error** via
  `addOnRequiresSetAdmission`. No warning needed.

### Translation to the three destinations, including the loss

| Destination | Mapping | Loss |
| --- | --- | --- |
| **schema.org** | `partOf.offers` → `superEvent` (`EventSeries`/`Event`) `.offers`. Part `offers` → the part `Event`'s `offers`. `scope: "add-on"` → the part `Offer` plus a `description` noting "in addition to conference admission" | **The `add-on` relationship**, and (inherently) the whole `superEvent` link — Google follows neither. A schema.org consumer that *does* follow `superEvent` gets the admission; the "additional" semantics degrade to text. |
| **iCal** | All price → `DESCRIPTION` / `X-OTE-PRICE` on each `VEVENT`; the admission repeated per part | Total price structure — the existing `offers` loss. `add-on` degrades to a `DESCRIPTION` line ("Workshop fee: €60, in addition to conference admission"). |
| **RSS / Atom** | Price in the item body | Same as `offers` today. |

### Alternatives considered

- **A dedicated `registration` object distinct from `offers`.** Rejected: it re-implements `price` /
  `currency` / `url` / `availability`, and `offers` already *is* the "how to attend and what it costs"
  model. `partOf.offers` reuses it verbatim.
- **Path A from Round 1 (silent parent→part inheritance as a MUST).** Rejected in Round 1 and still
  rejected — rule (3) is the safe, scoped version.
- **`offers[].scope` as a boolean `requiresAdmission`.** Considered. An enum is chosen so a third
  relation (e.g. `"replaces"` — a per-part price that supersedes the admission for people who only want
  that part) can be added later without a breaking change, and because "absent boolean = false" is
  exactly the tolerant default the spec avoids elsewhere.
- **Model it as feed→event inheritance** (like `license`). Rejected: the parent of a `multipart` event is
  not the feed, and parts can span feeds.
- **A `parentOffers` field at event level instead of inside `partOf`** (Round 1's Path C). Functionally
  equivalent to `partOf.offers`; `partOf.offers` is chosen because the shared price *belongs to the set*,
  which is exactly what `partOf` identifies, and co-locating `name`/`url`/`offers` for the set keeps them
  from drifting apart.
- **Codex Round 4's cleaner alternative: require a real parent OTE document, put canonical admission
  offers there with stable offer `id`s, `partOf.offers` is only a denormalised cache; add-ons carry
  `dependsOn: [<parent-offer-id>]`.** This *is* Model B, plus mandatory parent publication. Rejected as
  the v0.5 baseline for one reason: **C6 is real and common** — most conferences' `partOf.id` is an
  HTML page, not an OTE document, and a model that only works when the organiser publishes a second OTE
  document for the umbrella is a model that does not work for the majority. `partOf.offers` in every part
  is the denormalisation that makes C6 work. Model B's offer-`id`/`dependsOn` layer is kept as the
  documented extension for when tier-specific coverage is actually needed.

### Decisions touched (Codex Round 4 enumerated these; confirmed)

**Implementation guidance (Codex Round 5):** the new P037 entry is the **primary** decision. The older
entries below are *extended by cross-reference from* the P037 entry — do not rewrite their settled
rationale in place; add a "P037 extends this to …" line.

| Decision | What P037 does to it |
| --- | --- |
| **new (primary)** | A `DECISIONS.md` entry for P037: the `0.5.0` breaking change (unprefixed-collision risk), the `partOf`-safely-ignorable wording change, the URL-only "relationship known / total unknown" semantics for `add-on`, and the `sharedOffersConsistent` JSON-equality definition (array order significant, member order not, JSON-value numeric equality — `45`≡`45.0`, exact strings, `null` treated as absent, omitted siblings allowed, translations-map members order-insensitive). |
| **D009** | `offers[].opensAt`/`closesAt` window validation now also applies at `partOf.offers[]` — add tests at the new path. No semantic change. |
| **D010 / D023** | `distinctTranslationLanguages` and the base `textLanguage` requirement must enumerate `partOf.offers[].translations` as a translations-map site. |
| **D011** | The feed-root custom-keyword pattern gains `sharedOffersConsistent` — needs its own decision because the equality relation is nested JSON, not one id string. |
| **D012** | `partOf.id ≠ event.id` unchanged and still enforced after adding `offers` under `partOf`. |
| **D021** | `currency` requires `price`, `currency` without `price` invalid — must hold unchanged at `partOf.offers[]`; add invalid examples. |
| **D030** | The primary-text warning extends to `partOf.offers[].name` when `partOf.offers[].translations` exists and the primary `name` is absent. |
| D004, D015, D025 | No semantic change; noted for test coverage and feed-root validation ordering. |

### Revisit if

A real producer needs **Model B** (tier-specific coverage / per-day passes / `dependsOn`), or
schema.org / Google start following `subEvent` for offers (which would remove the one inherent loss).

## P038 — a "Suggested extensions" section on the site

**Area:** the website (`docs/`), the README §Extensions. **Not a schema change.**

### Problem

The spec already has a good mechanism for growth — unprefixed extension fields graduate to core once
"somebody already really uses" them (§Extensions). But there is **no visible list** of which fields are
candidates, what shape they should take, or how much adoption they have. So every borderline field
(`recordings` was the trigger) turns into a binary yes/no argument at proposal time, with no way to
gather the evidence that would settle it. hhkaos: *"quizás deba haber un apartado en la web con
extensiones sugeridas y cómo usarlas para poder evaluar en un futuro si hay suficiente adopción."*

### Proposal — a *generated* page, backed by a checked-in registry

Codex Round 4: a prose-only page with a hand-edited adoption count "will drift and become advocacy
instead of evidence." Agreed. So:

1. **`docs/data/suggested-extensions.json`** — the source of truth, checked in. One entry per candidate:
   ```jsonc
   {
     "name": "recordings",
     "purpose": "Links to published recordings of the event, added after it happened.",
     "scope": "event",                       // or "feed"
     "shape": { "$ref": "…/recordingEntry" }, // or an inline JSON snippet
     "status": "gathering-evidence",          // gathering-evidence | proposed-for | graduated | withdrawn
     "statusVersion": null,                   // e.g. "0.6.0" once proposed/graduated
     "graduationQuestion": "Do ≥3 adopter feeds emit it with this shape?",
     "observedAdoption": { "feeds": 0, "asOf": null }  // written by the scan, not by hand
   }
   ```
2. **A key-scan added to the existing feed tooling** (`scripts/check-feeds.mjs` already fetches every
   registered adopter feed for the health check). For each `suggested-extensions.json` entry, count how
   many adopter feeds contain that key, write `observedAdoption` back. Runs in the same CI job as the
   health check; the count is never hand-edited.
3. **The public page is generated** from `suggested-extensions.json` (same pattern as the reference docs
   and the examples gallery, which are already generated and CI-checked for drift). A short pointer is
   added to README §Extensions.
4. **Process text** (lightweight, on the page and in `CONTRIBUTING.md`): the maintainer owns the
   registry file; CI owns the count; each entry must state its `graduationQuestion`; a field moves to
   `proposed-for` only via a normal proposal, and to `graduated` only when it ships in a version.

Seed entries: `sponsors`, `capacity`, `level`/`audience` (README open question), the **`speakers`
enrichment block** and **`event.sameAs`** below. (`feed.alternates` #25 and `feed.contributing` #26 went
straight into v0.5 as P039/P040; `recordings` went in as P036; `speakers[].sameAs` went into the P035
core.)

#### Seed: the `speakers` enrichment block

`speakers[].sameAs` went into the P035 core (Round 10). The rest of what hhkaos raised from
techconf.directory's speaker records gets a **recommended extension shape** here, so early adopters
converge instead of each inventing one:

```jsonc
"speakers": [
  {
    "name": "Ada Lovelace",
    "url": "https://ada.example",             // core (P035)
    "sameAs": ["https://fosstodon.org/@ada"], // core (P035)
    // --- enrichment (unprefixed extension until graduated) ---
    "affiliation": "Analytical Engines Inc.", // ONE org display name — a proper noun, not translated
    "jobTitle": "Principal Engineer",         // free text (document's textLanguage)
    "bio": "Works on compilers and calculus of operations.",  // free text prose
    "image": [                                // SAME shape as event image[]; its .translations is NOT core-validated here
      { "url": "https://ada.example/photo.jpg", "alt": "Ada Lovelace, head and shoulders" }
    ]
  }
]
```

**One registry entry per sub-field** (Codex Round 9 — an umbrella `speakers.*` entry can't carry
independent status). `docs/data/suggested-extensions.json`:

```jsonc
{ "name": "speakers[].affiliation", "scope": "event",
  "purpose": "The speaker's organisation, as one display name.",
  "shape": "string (proper noun, written once, not translated — like organizers[].name)",
  "status": "gathering-evidence",
  "graduationQuestion": "≥3 producers emit it?",
  "observedAdoption": { "feeds": 0, "asOf": null } },
{ "name": "speakers[].jobTitle", … "graduationQuestion": "≥3 producers, AND worth a local translations map (D010/D023/D030)?" },
{ "name": "speakers[].bio",      … },
{ "name": "speakers[].image",    … "graduationQuestion": "≥3 producers, AND worth reopening the image[].alt apparatus nested in speakers[]?" }
```

**`speakers[].image[].translations` is not core-validated** while `image` is an extension — the
D010/D023/D030 keywords enumerate a fixed set of translations-map sites and would only cover `speakers[].*`
after a future normative adoption. The page says so.

`affiliation` is one **organisation display name, written once** — the same "choose the audience-
recognisable spelling, do not put two" rule the spec already applies to `organizers[].name` and to
locality spellings. It is not free prose and not translated.

#### Seed: `event.sameAs` — an aggregator's re-listing hint

Raised by hhkaos from [eventos.wiki](https://eventos.wiki/events.json), an aggregator that mints its own
`id` for third-party events (e.g. "Codemotion Madrid 2027") and whose `url` and `organizers[].url` both
point back at eventos.wiki — so the thread back to the organiser's canonical page is lost.

**The idea.** `event.sameAs` — an array of HTTP(S) IRIs the publisher asserts describe the **same event**
(the organiser's canonical page, another OTE `id`, a well-known listing). Maps to schema.org `Event.sameAs`
(the `Thing` property, same family as `speakers[].sameAs` → `Person.sameAs`). A consumer combining feeds
can collapse records that share a `sameAs` target — deduplication driven by a **publisher assertion**, not
a heuristic.

**Why P038 and not core.** The spec explicitly lists *"Deduplication across sources"* in "What v0.4 does
not solve" (line 844) — a load-bearing non-goal. `sameAs`, however carefully framed as "a hint, not the
heuristic", is a step into that space, and that deserves adoption evidence + a deliberate `DECISIONS.md`
graduation, unlike `recordings`/`speakers[].sameAs` which reversed no stated non-goal. It is also the
*clearest* P038 candidate: one real producer (eventos.wiki), which does not emit it yet but would.

**Two things it is NOT, and a mechanism that already half-exists:**

- **Not `id`.** `id` stays the per-publisher stable identifier — that is what makes *updates* work
  (eventos.wiki re-publishing its own record). `sameAs` is orthogonal: same-event, different-record.
- **Not the heuristic.** No fuzzy name/date/venue matching enters the spec; a consumer still only
  *trusts* a `sameAs` the publisher wrote.
- **`source.url` already carries part of this.** `source` is **required** when an event is *aggregated*
  (`README.md:389`) — eventos.wiki's example is **missing it**, which is arguably a conformance gap worth
  raising with that adopter. `source.url` = "the original record" (provenance: *I got this from here*).
  `sameAs` = identity (*this IS the thing at here*). Often the same URL; a consumer could reasonably use
  `source.url` as a weak dedup anchor today. A dedicated `sameAs` is the stronger, explicit form.

Registry entry:

```jsonc
{ "name": "sameAs", "scope": "event",
  "purpose": "URLs the publisher asserts describe the SAME event — for cross-aggregator dedup.",
  "shape": "array of HTTP(S) IRIs, uniqueItems, no userinfo — maps to schema.org Event.sameAs",
  "status": "gathering-evidence",
  "graduationQuestion": "Do ≥2 aggregators emit it pointing at a shared canonical URL? And does the 'dedup is out of scope' non-goal need revisiting, or does 'publisher hint ≠ heuristic' hold?",
  "observedAdoption": { "feeds": 0, "asOf": null } }
```

### Why it is worth doing now

- It makes the §Extensions promise ("this is how the spec grows") **operational** instead of aspirational,
  and it does so *without weakening it* — the graduation bar stays "real use", now with a number behind it.
- It gives `0.x` a legible way to say "we're not sure yet" that is not just an issue thread.
- It costs one registry file + one scan function in tooling that already loops over the same feeds + one
  generated page. No schema, no normative weight (non-normative, like `DECISIONS.md`).

### Interaction with P036

`recordings` (P036) is a v0.5 field (hhkaos confirmed, over the P038-page alternative). P038's seed
entries are `sponsors`, `capacity`, and `level`/`audience` — **not** `feed.alternates` or
`feed.contributing`, which hhkaos moved into the v0.5 bundle as **P039/P040** below.

## P039 — `feed.alternates`: the same collection, in other formats

**Area:** `feed.schema.json` only. **Not the Event Schema.** Issue
[#25](https://github.com/openTechEvents/opentechevents-spec/issues/25).

### Problem

The v0.4 Discovery section covers the *symmetric* problem — how to find the OTE feed **from an HTML
page** (`<link rel="alternate" type="application/ote+json">`). The gap is when there is **no HTML page**:
an OTE feed served as a bare JSON endpoint, or a client that consumes the JSON directly and will not
parse HTML. There is nowhere — not in HTML, not in OTE — for the publisher to say "this same collection
is also available as RSS here, or iCal here". Readers (`reader.opentechevents.org`), embeds
(`ote-subscribe`), and multi-feed aggregators all want this so they can offer "subscribe in the format
you prefer" without a per-source hand-mapping.

### Proposal

Feed-level, optional, **a list**:

```jsonc
"alternates": [
  { "mediaType": "application/rss+xml", "url": "https://pyalmeria.example/events.rss" },
  { "mediaType": "text/calendar",       "url": "https://pyalmeria.example/events.ics" }
]
```

`$defs` (in `feed.schema.json`):

```jsonc
"alternates": {
  "description": "Where this same collection of events is published in other formats — RSS, iCalendar, schema.org JSON-LD. The JSON form of an HTML <link rel=\"alternate\"> / the Link: rel=\"alternate\" HTTP header, for feeds that have no HTML page in front of them. INFORMATIONAL: OTE does not guarantee the linked resources are generated from this feed or kept in sync with it — see the note below.",
  "type": "array",
  "minItems": 1,
  "uniqueItems": true,
  "items": { "$ref": "#/$defs/alternate" }
},
"alternate": {
  "type": "object",
  "required": ["mediaType", "url"],
  "properties": {
    "mediaType": {
      "description": "IANA media type of the alternate representation (application/rss+xml, text/calendar, application/ld+json). A loose shape check, not a closed list — new formats appear.",
      "type": "string",
      "pattern": "^[a-z]+/[a-z0-9][a-z0-9!#$&^_.+-]*$",
      "examples": ["application/rss+xml", "text/calendar", "application/ld+json"]
    },
    "url": {
      "description": "Absolute HTTP(S) IRI of the alternate representation. Shared URL rules — no embedded credentials.",
      "type": "string", "format": "iri", "pattern": "^https?://",
      "not": { "pattern": "^https?://[^/?#]*@" }
    }
  }
}
```

**`mediaType` is a bare, lowercase media-type token — no parameters** (`application/rss+xml`, not
`application/rss+xml; charset=utf-8`, not `Application/RSS+XML`). The pattern enforces it. It accepts the
real feed types (`application/atom+xml`, `application/feed+json`, `application/ld+json`, `text/calendar`,
`application/vnd.*+json`) and rejects a full `Content-Type` header value or a bare word (Codex Round 7
verified this against the pattern). It is a canonical token for matching, not an HTTP header to echo.

**No `title`.** The issue floated an optional one; dropped. `mediaType` already tells a client what the
link is, and a client renders "RSS" / "iCalendar" in the reader's language from the media type — the same
"an enum is multilingual for free" reasoning the spec uses for `status`/`eligibility.type`. A free-text
`title` would drag in the whole `translations` question for a label nobody needs to write.

**Two entries MAY share a `mediaType`** (a publisher with two RSS mirrors). `uniqueItems` rejects only
exact duplicates. A consumer that can show one shows the first — the `image[]` rule. **Same-`mediaType`
entries SHOULD be mirrors or equivalent choices**, not semantically different feeds that would need a
human label; if a real case needs labels, `title` is revisited (see "Revisit if").

### The sync risk — resolved as "informational, with a producer SHOULD"

The issue names it: if the linked `.ics`/RSS is **not** generated from the OTE feed but maintained
separately, the two can drift with no validator noticing. **Decision: `alternates` is informational.**
The consumer contract: treat each entry as "another representation the publisher points to", and **MUST
NOT assume exact sync, completeness, or derivation** from the OTE feed. The producer duty (Codex Round 7):
alternates **SHOULD** be generated from the same source, or otherwise intended to describe the same
collection. The stronger alternative — the publisher *warrants* they stay in sync — is a promise no schema
can check and few publishers could keep. A prose paragraph in §Discovery says both halves.

### Compatibility impact

Purely additive to `feed.schema.json`. No v0.2–v0.4 feed becomes invalid. The one §Extensions
collision caveat applies (a publisher already shipping `alternates` with a different shape) — small,
noted in the migration note alongside P037's.

### Recommended profile

**Not recommended.** A community feed with an HTML page already has `<link rel="alternate">` and does not
need this; a feed without alternates is not "less useful", it just has one representation. No warning.

### Translation to the three destinations

Not an event field — it is metadata *about the feed*. It maps **outward** to HTML/HTTP, not to the three
event destinations: `<link rel="alternate" type="<mediaType>" href="<url>">` in `<head>`, and the
`Link: <url>; rel="alternate"; type="<mediaType>"` HTTP header. An importer going the other way (HTML →
OTE) can populate `alternates` from exactly those.

### Alternatives considered

- **Only `<link rel="alternate">` in HTML, no JSON field.** Rejected — that is the status quo, and it
  fails precisely for the no-HTML-page case the issue is about.
- **A closed `mediaType` enum.** Rejected — RSS, Atom, iCal, JSON-LD, and whatever comes next; a loose
  pattern is enough and does not go stale.
- **`{ format: "rss" | "ical" | "jsonld" }` instead of a media type.** Rejected — the media type is the
  thing HTML and HTTP already use; reusing it makes the round-trip trivial.

### Revisit if

A real need appears for the publisher to declare "these alternates ARE machine-generated from this feed"
(a boolean `derived: true`), or for a per-alternate `title` once someone hits a case the media type
cannot disambiguate.

## P040 — `contributing`: where to report or fix a wrong datum

**Area:** `feed.schema.json` **and** `event.schema.json` (`$defs/event.properties`, inherited). Issue
[#26](https://github.com/openTechEvents/opentechevents-spec/issues/26).

### Problem

A feed reader or aggregator wants to show, next to each event, a "report an error" / "suggest a
correction" link. Today there is no field for it, and the fields that look close do not fit:

- **`organizers[].email`/`url`** is the organiser's contact, not a correction channel — and an
  **aggregator** feed **must omit `organizers`** (D016), so the publisher who most needs "report me an
  error" is exactly the one with no field to use.
- **`source.url`** points at *where the data came from* (a `.ics`, a Meetup page) and only exists for
  imported events. The common case — a community publishing its own event — has no `source`. And "fix it
  upstream" (the Meetup page) does not fix a mapping bug introduced by the aggregator.

### Evidence — real producers already exist, in two forms

- **Web app / issue tracker.** The OTE editor (`tools.opentechevents.org/editor/`) already supports
  `?repo=owner/name`: it reads the repo's preset and **proposes changes via issue → PR** (`docs/data/tools.json`,
  "editor" entry). What is missing is a way for a feed to *announce* the URL so a reading tool renders
  the button without a hand-paste.
- **Email.** [dev.events/about](https://dev.events/about) points contributors at `hello@dev.events` for
  corrections and additions. An `hello@` / `corrections@` role address is a real, common corrections
  channel — for a directory that has no public issue tracker it is often the *only* one.

Both clear the producer bar more cleanly than `cfp` did.

### Proposal

A single URL, **feed-level and event-level**, inherited feed → event with **default-value semantics** —
the simplest inheritance the spec has, identical to `license`/`specVersion`/`textLanguage`: an event that
declares its own **replaces** the inherited value (it is a scalar, so there is no list-merge question).

```jsonc
// feed:
"contributing": "https://github.com/pyalmeria/eventos/issues/new"

// an event in an aggregator's feed, from a community with its own repo:
"contributing": "https://tools.opentechevents.org/editor/?repo=rustmadrid/events&id=…"
```

**A shared `$def`, `$ref`'d from both levels** (Codex Round 7 — the first draft said "shared" but inlined
it). `spec/v0.5/event.schema.json#/$defs/contributing` holds the string schema; `feed.schema.json`
references it cross-schema by `$id`, exactly as `feed.license` / `feed.textLanguage` / `feed.updatedAt`
already do. `x-inheritsFrom: "feed.contributing"` sits as a **sibling annotation on the event property
only** — the feed property is the *source* of the default, not an inheritor.

```jsonc
// spec/v0.5/event.schema.json  #/$defs
"contributing": {
  "description": "URL for reporting or proposing a data change — an issue tracker, a form, an OTE editor deep link (?repo=…), or a mailto: role address.",
  "type": "string",
  "anyOf": [
    { "format": "iri", "pattern": "^https?://", "not": { "pattern": "^https?://[^/?#]*@" } },
    { "pattern": "^mailto:[^\\s?@,#/\\[\\]]+@[^\\s?@,#/\\[\\]]+$" }   // ONE bare address; no ?headers, no ,second, no #frag
  ]
}

// feed.schema.json  #/properties
"contributing": { "$ref": "https://opentechevents.org/schema/v0.5/event.schema.json#/$defs/contributing",
                  "description": "…the default every event inherits when it omits its own." }

// event.schema.json  #/$defs/event/properties
"contributing": { "$ref": "#/$defs/contributing", "x-inheritsFrom": "feed.contributing",
                  "description": "…inherited from feed.contributing unless declared here." }
```

**It accepts an HTTP(S) IRI *or* a `mailto:` URI** (added after hhkaos pointed at dev.events'
`hello@dev.events`). The `mailto:` branch is deliberately **stricter than RFC 6068**: exactly one bare
address, **no `?` headers** (not a prefilled-message template — it is a stable contact pointer), **no `,`
second recipient**, **no `#` fragment**, and no raw `/` `[` `]` (RFC 6068 §2 says those must be
percent-encoded). Codex Round 8 verified the tightened pattern against RFC 6068 and against Ajv.

> **P040-local rule (Codex Round 8 — not just a cross-reference).** `contributing` is top-level and
> **inherited**, so it is filled once and exposed on every event in the feed — a bigger spam surface than
> `organizers[].email`. So, in `contributing`'s own prose:
> - **A role/public address only** — `hello@`, `corrections@`, `info@` — never a person's mailbox.
> - **A tool MUST NOT populate `contributing` from a source that is not itself publicly published**
>   (a private `.ics`, an internal export). Same rule as `organizers[].email`, stated here because the
>   data is contact data.
> - **A consumer MUST use it only for corrections to this record** — not a mailing list, not a contacts
>   database. Unenforceable by any schema, like the `status`-update rule; stated anyway.

**D020/D026 note.** D020 (`id`/`partOf.id` must be HTTP(S)) is **not** reopened — it is about *identity
and uniqueness*, and `contributing` is a contact pointer, not an identifier. D026 (no embedded userinfo
in HTTP(S) URLs) has no `mailto:` authority component to apply to, but its "do not put a secret in a
public link" principle is exactly why the `mailto:` branch allows only one bare role address with no
headers. `contributing` is the first spec field to accept a non-HTTP scheme; this note goes in its
`DECISIONS.md` entry.

**Name: `contributing`** (Codex Round 7 concurs). Matches `CONTRIBUTING.md`; the spec favours short names
(`url` not `registrationUrl`); `correctionsUrl` is too narrow for "fix *or* contribute a data change";
`contributingUrl` is redundant when the type is always HTTP(S) — `licenseUrl` is only split because
`license` is *SPDX-or-URL*. The generated reference label is made explicit: *"URL for reporting or
proposing data changes."*

**A single value, not a structured object.** The issue asks whether to distinguish "report" from "edit
yourself". No — minimum until a producer asks: a plain issues URL *is* "report", an editor `?repo=` link
*is* "edit", a `mailto:` *is* "write to us", and one field holding whichever the publisher chose covers
all three. Widening string → object later is a breaking change and would arrive with its own version,
exactly as `cfp` reserves.

### Compatibility impact

Purely additive at both levels. Inheritance reuses the existing default-value mechanism — no new keyword,
no feed-root check. The §Extensions collision caveat applies (noted with the others).

### Recommended profile

**Not recommended.** An `.ics` importer never has it; and an event without a correction link is not
unusable, just slightly less maintainable. Adding a warning would push every self-publishing community to
create an issue tracker they may not want. Same reasoning as `email`.

### Translation to the three destinations

Like `cfp`, **it travels nowhere**: no schema.org term, no iCalendar property, nothing in RSS/Atom. On
export it degrades to a line in `DESCRIPTION` or is dropped. Its value is entirely inside the OTE
ecosystem — a reading tool rendering a "suggest a correction" button — and that is stated out loud, the
way `cfp`'s is.

**Does not overlap `source.url` or `organizers[].email`** (Codex Round 7 verified). `source.url` is
*provenance* — where imported data came from, upstream. `organizers[].email` is *who to contact about the
event*, and an aggregator must omit it. `contributing` is *where to fix this record* — including an
aggregator's own mapping error, which neither of the other two can point at. The implementation ships one
example carrying **both** `source.url` and `contributing` so the distinction is visible.

### Alternatives considered

- **Reuse `organizers[].email`.** Rejected — an aggregator must omit `organizers`, and a correction
  channel is not the organiser's inbox.
- **Reuse/extend `source`.** Rejected — `source` is upstream provenance and only exists for imported
  events; the common self-publishing case has none.
- **Feed-level only, no event override.** Rejected — the real case (an aggregated event from a community
  with its own repo, wanting its own link, distinct from the aggregator's general channel) needs the
  override, and it costs nothing (the inheritance mechanism already exists).
- **A structured `{ report, edit }` object.** Deferred — no producer emits both yet.

### Revisit if

A producer emits a structured value (separate "report" and "edit" URLs), or a `rel`-type registration
makes an HTML/HTTP mapping possible.
